# IDD software tools database

This file holds the data underlying the "IDD tools" section of the Global Society for Infectious Disease Dynamics ([gsidd.org](http://gsidd.org)) website. It lists software packages and tools of use or interest to the infectious disease dynamics (IDD) community, following the definitions and inclusion criteria set out in [details.md](details.md).

Entries are drawn from a prior 189-entry compilation, re-vetted in full against the current criteria, plus a keyword-based search for tools the earlier compilation had missed. Tools that do not qualify are listed, with the reason, in [excluded_tools.md](excluded_tools.md) rather than being deleted silently.

## Schema

Each tool is one row of the main table. The first nine columns are those specified in [details.md](details.md); `Usage` and `Licence` are added so that the evidence behind two of the inclusion criteria is visible rather than implicit.

| Column | Description |
|---|---|
| Name | Tool name, as used by its developers |
| Type | One of `Model`, `Utility`, `AI extension` (controlled vocabulary, below) |
| Discipline | Primary disciplinary home of the tool (controlled vocabulary, below) |
| Pathogen | Pathogen or pathogen group the tool targets (controlled vocabulary, below) |
| Language | Implementation language(s) |
| Description | One-sentence summary of what the tool does |
| Authors | Originating individual(s), lab(s), or institution(s) |
| Code | Markdown link to the source repository or project page; link text is the bare domain |
| Publication | Markdown link to the DOI of the tool's publication; `—` if none |
| Usage | `Established`, `Emerging` or `Minimal` (scored as below), followed in parentheses by the evidence behind it — GitHub stars and forks, package-repository downloads, or documented institutional adoption |
| Licence | SPDX identifier where the tool is open source; an explicit description otherwise. Anything that is not an OSI-approved open-source licence is stated as such |

### Controlled vocabulary: Type

- **Model** — the tool's core is a representation of transmission or disease dynamics, whether by simulation (agent-based, compartmental, network, metapopulation) or by mechanistic or statistical inference of transmission quantities.
- **Utility** — the tool solves a supporting problem rather than representing transmission itself: data access, cleaning, validation and visualisation; sequence and phylogenetic processing; surveillance analytics; forecast evaluation; synthetic population generation.
- **AI extension** — AI-based agents, skills, MCP servers and LLM plugins for performing IDD tasks. No tool currently meets the inclusion criteria under this Type; the category is defined and left open for submissions.

### Controlled vocabulary: Discipline

`Epidemiology` · `Public health` · `Global health` · `Math & stats` · `Computer science` · `Genomics` · `Ecology` · `Veterinary`

`Immunology` and within-host disciplines are part of the vocabulary but are not currently used by any entry. Each tool is assigned the single discipline that best describes where it was developed and where its primary user community sits, not every discipline that uses it.

### Controlled vocabulary: Pathogen

`Any/general` · `Respiratory` · `Vector-borne` · `Malaria` · `NTDs` · `STIs` · `HIV` · `TB` · `Enteric` · `Vaccine-preventable` · `Zoonotic`

`Any/general` is used for pathogen-agnostic frameworks and methods. `Malaria` and `HIV` are broken out from `Vector-borne` and `STIs` respectively because of the size of those tool communities.

### Usage scoring

Every tool is scored out of four sources of evidence, each converted to points at a stated rate: **1 point** per GitHub star and per fork; **1 point** per 1,000 package downloads, counting all-time CRAN and PyPI totals; **1 point** per citation of the tool's foundational paper; **1 point** per country with documented use. The total sets the label: **Established** above 50 points, **Emerging** at 10–50, **Minimal** below 10.

The points themselves are not published, because the four sources are not really commensurable and a single number would claim a precision the inputs do not have — a star, a download and a citation are alike only in being countable. The label is a coarse summary, deliberately; the evidence in parentheses after it is what the label was derived from, and is the part to argue with. Tools distributed through national programmes rather than package repositories score only on citations and documented country use, which under-counts them, and tools whose foundational paper is recent score low on citations regardless of how widely they are used. `docs/fetch_usage.py` computes all of this; `docs/data/usage.json` holds the per-tool breakdown, so any label can be checked against its inputs.

## Methodology and caveats

**Snapshot date: 2026-08-07**, with the `Usage` column re-scored on 2026-08-14. All counts, dates and statuses were checked on those dates and will drift.

**How the inclusion criteria were applied.** The five criteria in details.md were treated as follows.

1. **Open source** — checked via the GitHub licence API, the `License` field of the CRAN `DESCRIPTION`, or by reading the `LICENSE` file directly where the API reported an unrecognised licence. Tools that are *not* open source are **included but explicitly labelled** in the `Licence` column, since several of the most consequential tools in the field (Spectrum, GLEAM, LiST, SaTScan) are closed source and omitting them would misrepresent the landscape. Two tools were found to have non-open licences despite public GitHub repositories: **FRED** (a University of Pittsburgh EULA) and **Episimmer** (Commons Clause).
2. **Published** — Crossref bibliographic and title queries, supplemented by `CITATION.cff` files. An automatically minted CRAN or Zenodo DOI is recorded as `—` rather than as a publication, because it evidences distribution rather than peer review. **Publication is not a hard gate**: a tool with substantial independent evidence of use qualifies without a paper, and a number of widely used packages are included on that basis.
3. **Documented** — installation instructions, at least one getting-started example or vignette, and a technical reference. Assessed by inspection; this is the least mechanised of the five checks and therefore the least consistent.
4. **Evidence of use** — assessed cumulatively rather than as a single threshold: GitHub stars and forks, all-time CRAN and PyPI downloads, citations of the foundational paper, and documented adoption by agencies or national programmes, combined into the points total described under [Usage scoring](#usage-scoring) and reported as `Established`, `Emerging` or `Minimal`. Inclusion does not require a particular label — `Minimal` records that the public evidence is thin, not that the tool is unimportant. Tools whose users are in government or agency workflows rather than on GitHub remain the hardest to assess and the most likely to be under-counted, which is why documented country use is counted at all.
5. **Supported** — any repository push, or CRAN/PyPI release, on or after 2023-08-07, and the repository not archived. Deliberately a low bar: a quiet repository may simply mean a tool that is finished. Tools known to be retired are labelled as such in the `Description` column regardless of commit activity — currently **EMOD**, which its maintainers have confirmed is no longer supported.

**What was searched for gaps.** No author or project names were used as query terms. The first pass combined Crossref bibliographic queries pairing modelling terms (epidemic, outbreak, transmission, metapopulation, agent-based, compartmental, nowcasting, phylodynamic) with software terms (package, framework, library, toolkit, simulator, pipeline); GitHub repository search by topic and keyword, sorted by stars; GitHub search for AI-extension terms (`mcp-server`, `llm`, `agent`, `copilot`) combined with epidemiology terms; and the CRAN *Epidemiology* Task View.

**A second pass, after a documented miss (2026-08-08).** That grid missed [Naomi](https://doi.org/10.1002/jia2.25788), the Bayesian small-area model behind UNAIDS's district-level HIV estimates, and it missed it twice over. Its modelling terms were all *transmission-dynamics* words, so a paper about "estimating HIV epidemic indicators" by "small-area estimation" matched none of them; and its software terms were all *developer* words, so a "modelling tool" described as an "interactive web-based software tool" matched none of those either. Anything that infers burden from survey and programme data — rather than simulating spread — was invisible to it, as was anything whose paper is written for a health audience rather than a methods one.

Two axes were therefore added and re-run. Estimation and mapping: `small-area estimation`, `disease mapping`, `prevalence mapping`, `model-based geostatistics`, `spatial disaggregation`, `burden estimation`, `subnational estimates`, `evidence synthesis`, `incidence estimation`, `risk mapping`. Immunity and serology: `seroprevalence`, `serological survey`, `force of infection`, `serocatalytic`, `seroincidence`, `antibody kinetics`. Both were crossed with a wider set of software terms — `tool`, `software`, `application`, `web-based tool`, `shiny app`, `platform`, `dashboard`, `calculator` — alongside the original six. This added nine entries: Naomi, first90, disaggregation and prevR from the first axis, and serofoi, serosolver, serosim, Rsero and serocalculator from the second. `serofoi` was already named as an Epiverse-TRACE component in [database_ecosystems.md](database_ecosystems.md) while absent from this table, which is a reminder to reconcile the two files against each other as well as against the literature.

**Honest limitations.** Keyword search only finds tools that describe themselves in the vocabulary being searched for, and the Naomi miss shows how expensive a narrow vocabulary is: two whole method families were absent, not one tool. Others are presumably still missing on the same principle, and the most likely candidates are tools whose papers avoid the word "model" altogether. The documentation criterion is a judgement call and borderline entries could reasonably move either way. Usage metrics are not comparable across languages or distribution channels — CRAN, PyPI, GitHub and installer-based tools are counted in fundamentally different ways, and tools distributed as desktop applications or through national programmes have no download counter at all; the points that produce the `Usage` label paper over that incomparability with fixed exchange rates, which is defensible only as a coarse ordering and not as a measurement. The search was English-language and Crossref/GitHub/CRAN/PyPI-indexed, so tools published in other languages, distributed on institutional servers or non-GitHub forges, or documented only in grey literature remain under-represented. Discipline and Pathogen are single-valued by design, which loses information for cross-cutting tools. Excluding a tool is a statement about fit against these criteria on this date, not a judgement of quality.

**Conflicts of interest**: this database was compiled by Cliff Kerr, who works at the Institute for Disease Modeling (IDM), leads development of Starsim, and is a co-author on several of the publications referenced. Ordering within the table is alphabetical and implies no ranking. Corrections and additions are welcome.

## Gaps and known limitations

**No `AI extension` entries.** A dedicated search was run for IDD-specific AI agents, MCP servers, Claude skills and LLM plugins: GitHub repository search on `epidemiology`/`public-health`/`outbreak`/`disease` combined with `mcp-server`, `llm`, `agent` and `copilot`, plus Crossref queries for LLM agents and copilots in epidemic modelling. Candidates found fall into three groups, none of which qualifies:

- **General biomedical MCP servers** (PubMed, ClinicalTrials.gov, CDC WONDER, healthcare data servers, some with 100+ stars). These are widely used but are not unique to IDD, and none has a publication.
- **IDD-specific MCP servers and dashboards** (for example WHO Disease Outbreak News, PopHIVE public-health data, pandemic biosurveillance servers). These are IDD-relevant but have 0–22 stars, no publication, and mostly no documentation beyond a README.
- **LLM forecasting research code** (for example PandemicLLM, which does have a peer-reviewed paper). These are replication packages for a specific study rather than reusable tools, and fail the documentation and evidence-of-use criteria.

The conclusion is that as of 2026-08-07 the IDD AI-extension ecosystem exists but has not yet produced anything that clears the bar set for the other two Types. This is worth re-checking on a much shorter cycle than the rest of the database.

**Under-covered areas.** NTD modelling, veterinary and livestock modelling outside Europe, within-host and immunological modelling, and health-economic modelling specific to IDD are all thinly represented here, in every case because the leading tools fail on licensing, documentation, or publication rather than because tools do not exist.
